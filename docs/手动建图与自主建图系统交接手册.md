## 0. 接手人先读这一页

### 0.1 一句话理解系统

这是一套运行在 ROS 2 Humble 上的“3D 定位感知 + 2D 栅格建图导航”系统：

```text
Livox MID360 点云和 IMU
        ↓
FAST-LIO2 估计机器人三维位姿
        ↓
把三维点云投影成二维 LaserScan
        ↓
slam_toolbox 按 FAST-LIO 位姿生成二维 /map
        ↓
手动模式：人驾驶小车覆盖环境
自主模式：frontier 探索器 + Nav2 自动驾驶覆盖环境
```

手动建图和自主建图不是两套 SLAM。两者共用同一条传感器、定位、Scan 投影和二维栅格建图主链；自主模式只是在这条主链上增加 Nav2、代价地图、阿克曼前沿探索、返航和任务收尾。

### 0.2 接手时必须遵守的红线

1. 实车自主测试必须有人在车旁，确保硬件急停可立即触达。
2. 不要同时运行手动建图和自主建图。
3. `robot-base.service` 正常运行时，不要再传 `start_base:=true`，否则可能出现串口占用或重复底盘驱动。
4. 不要单独重复启动 `fastlio_2d_slam.launch.py`、`pointcloud_to_laserscan`、`scan_qos_relay` 或旧二维雷达 launch。
5. 不要在共享 `.bashrc` 环境里直接运行自主建图；必须使用 `/opt/ros/humble` 和本工作空间的隔离环境。
6. 不要直接编辑 `build/` 或 `install/`；源码真相在 `src/`。
7. 不要把 `explore` 和 `ackermann_explore` 混淆；当前正式入口默认使用后者。
8. 不要把“仍有 frontier 但当前无可达候选”解释成探索完成。
9. 未完成物理标定前，不要凭感觉修改 TF、footprint、最小转弯半径或底盘控制含义。
10. `kill -9` 和突然断电不会执行最终地图保存；真紧急时先保证人车安全，地图损失是次要问题。

### 0.3 新同事建议按这个顺序接手

```text
阅读本手册
  ↓
确认机器人、网络、串口和底盘服务
  ↓
进入隔离 ROS 环境并检查包来源
  ↓
只启动手动建图，确认共同建图链
  ↓
执行自主探索 dry run，不让车移动
  ↓
只启动 autonomous_mapping，做单个 Nav2 目标测试
  ↓
在安全场地进行完整 autonomous_exploration
  ↓
保存日志、地图和验收结果
```

不要从完整自主探索直接开始。分层验证能快速判断问题位于共同建图链、Nav2、探索器还是底盘执行层。

## 1. 项目目标、边界与交付物

### 1.1 系统要解决的问题

机器人进入一个没有现成二维地图的环境后，需要完成：

- 用 MID360 和 IMU 估计自身连续位姿；
- 把三维环境转换为 Nav2 可使用的二维占据栅格；
- 手动或自动覆盖尚未观测区域；
- 保存可供后续 Nav2 `map_server` 加载的地图；
- 自主模式下满足阿克曼车辆不能原地旋转的运动约束；
- 异常退出或任务完成时尽可能安全停车并保留地图。

### 1.2 两种正式工作模式

| 模式 | 控制车辆的人/程序 | 启动入口 | 是否启动 Nav2 | 是否启动探索器 | 主要产物 |
| --- | --- | --- | --- | --- | --- |
| 手动建图 | 操作员发送 `/cmd_vel` | `manual_mapping.launch.py` | 否 | 否 | 二维 PGM/YAML；手动配置还提供三维累计点云能力 |
| 自主建图 | `ackermann_explore` 选目标，Nav2 规划控制 | `autonomous_exploration.launch.py` | 是 | 是 | 自主覆盖得到的二维 PGM/YAML |

另有一个重要的中间验证模式：

| 模式 | 启动入口 | 用途 |
| --- | --- | --- |
| 自主建图底座、不启动探索器 | `autonomous_mapping.launch.py` | 验证共同建图链 + Nav2 单目标导航，把探索决策问题与规划控制问题分开 |

### 1.3 系统交付物

二维地图由一对同名文件组成：

```text
map_name.pgm   # 栅格图像
map_name.yaml  # 分辨率、原点、占用阈值、图像名
```

手动模式默认目录：

```text
~/maps/manual_mapping/manual_YYYYMMDD_HHMMSS.pgm
~/maps/manual_mapping/manual_YYYYMMDD_HHMMSS.yaml
```

自主模式默认目录：

```text
~/maps/autonomous_mapping/autonomous_YYYYMMDD_HHMMSS.pgm
~/maps/autonomous_mapping/autonomous_YYYYMMDD_HHMMSS.yaml
```

这组文件可直接交给 Nav2 `map_server`。手动模式的 FAST-LIO 配置还开启 `/Laser_map` 三维累计点云和 `/map_save` PCD 保存能力；自主模式为控制长期负载而关闭这两项。

### 1.4 不属于当前核心建图链的内容

- Web 管理器可能调用同一启动入口，但它不是定位、建图或探索算法本身；
- `low_battery_manager` 是独立安全服务，不由自主探索 launch 管理；
- 共享工作空间里的其他导航、Autoware、相机、语音和旧二维雷达包不属于本系统；
- STM32 固件和完整底盘协议不在当前仓库中。

## 2. 软硬件清单

### 2.1 硬件层

| 硬件 | 作用 | 软件接口 |
| --- | --- | --- |
| WHEELTEC 阿克曼底盘 | 执行前进、倒车、转向 | `/cmd_vel` → ROS 底盘驱动 → STM32 串口 |
| Livox MID360 | 提供 360° 三维点云和内置 IMU | `/livox/lidar`、`/livox/imu` |
| Ubuntu 机器人主机 | 运行 ROS 2 全部节点 | SSH、本地图形桌面、systemd |
| STM32 下位机 | 执行底盘串口控制并返回状态 | `/dev/wheeltec_controller`，115200 baud |
| 硬件急停 | 现场最高优先级安全保护 | 不依赖 ROS 软件 |

项目记录中的稳定串口名是：

```text
/dev/wheeltec_controller
```

它曾指向 CH343 USB 串口。不要改成 Jetson 板载串口 `/dev/ttyTHS1`。

### 2.2 软件层

| 层级 | 技术/包 | 主要职责 |
| --- | --- | --- |
| 操作系统 | Ubuntu 机器人系统 | 驱动、进程、网络、systemd |
| 中间件 | ROS 2 Humble | Topic、Service、Action、TF2、Lifecycle、launch |
| 构建 | colcon + ament_cmake + C++17 | 编译工作空间 |
| 雷达驱动 | `livox_ros_driver2` | 发布 MID360 CustomMsg 和 IMU |
| 三维定位 | `FAST_LIO_ROS2` / `fast_lio` | 雷达惯性里程计、点云配准、连续 TF |
| 三维转二维 | `pointcloud_to_laserscan` | 从 body 点云生成 360° LaserScan |
| QoS 适配 | 自定义 `scan_qos_relay` | Best Effort 输入转 Reliable 输出，保持时间戳 |
| 二维地图 | `slam_toolbox` | 按 FAST-LIO 位姿生成 `/map` |
| 导航 | Nav2 | Lifecycle、costmap、BT、规划、控制、平滑 |
| 全局规划 | Smac Hybrid-A* | 规划满足最小转弯半径的 SE(2) 路径 |
| 局部控制 | MPPI Ackermann | 滚动优化符合阿克曼约束的速度指令 |
| 探索 | 自定义 `ackermann_explore` | frontier 检测、观察位生成、可达性验证、评分、任务状态机 |

| 安全停车 | 驱动 watchdog + `cmd_vel_shutdown_guard` + 探索器 stop burst | 指令中断、退出和任务完成时发零速 |
| 可视化 | RViz2 | 三维点云、二维地图、Scan、路径、探索标记 |

### 3.3 为什么强调隔离环境

共享 `wheeltec` 账号可能加载其他工作空间，其中可能存在另一套 Nav2/DWB。混用二进制和插件会造成：

- 配置字段与插件版本不匹配；
- 实际运行的 Nav2 不是本项目验证过的系统包；
- build 成功但运行加载到另一份库；
- 同名包、同名插件或 Python 模块来源不可控。

本工作空间通过 `zzj_nav2_isolation.sh` 过滤冲突的 Nav2 路径，自主探索 launch 还会在启动机器人进程之前二次校验包前缀。

### 3.4 哪些修改需要重新构建

- C++ 源码修改：必须重新构建；
- `package.xml`、`CMakeLists.txt`：必须重新构建；
- 新增 executable 或安装目录：必须重新构建；
- launch/YAML/RViz/行为树：`--symlink-install` 时通常能立即反映，但交接流程仍建议执行 build 和 `audit-install`，避免运行版本歧义。

不要因为 `install/` 中某个 YAML 看起来更新就直接编辑它。应把确认过的内容写回 `src/`，重新构建并审计。

## 4. 全系统技术架构

### 4.1 硬件到地图的共同数据链

```text
┌──────────────────────────────────────────────────────────────┐
│                       真实物理环境                           │
└──────────────────────────────┬───────────────────────────────┘
                               │ 激光回波、惯性运动
                               ▼
                     Livox MID360 + IMU
                               │
                               ▼
                       livox_ros_driver2
                  /livox/lidar       /livox/imu
                               │
                               ▼
                         FAST-LIO2
              位姿、TF、路径、配准点云、可选三维地图
                               │ /cloud_registered_body
                               ▼
                  pointcloud_to_laserscan
                               │ /scan_raw
                               ▼
                       scan_qos_relay
                               │ /scan
                               ▼
                         slam_toolbox
                               │ /map
                    ┌──────────┴──────────┐
                    ▼                     ▼
              map_autosaver       Nav2 / 探索器（自主模式）
```

### 4.2 手动模式控制闭环

```text
操作员观察 RViz 和现场环境
          ↓
teleop_twist_keyboard 或其他控制源
          ↓ /cmd_vel
WHEELTEC ROS 驱动
          ↓ 串口控制包
STM32 + 阿克曼底盘
          ↓ 车辆运动
MID360 获取新环境观测
          ↓
共同建图链更新 /map
          ↓
操作员决定下一步驾驶方向
```

手动模式中，地图系统不决定车辆去哪里。地图质量依赖共同建图链、人工路线、速度、环境几何和传感器状态。

### 4.3 自主模式的三层闭环

自主模式包含三个不同时间尺度的闭环：

```text
任务层：ackermann_explore
  frontier → 候选观察位 → 路径预检 → 选择下一个目标
                           │ NavigateToPose
                           ▼
导航层：Nav2
  global costmap → Smac 路径 → BT 恢复 → MPPI 控制
                           │ /cmd_vel
                           ▼
执行层：底盘
  ROS 驱动 → STM32 → 转向/驱动 → 里程计反馈和新传感器观测
                           │
                           └───────────────回到地图和代价地图
```

理解这三层非常重要：

- 探索器决定“下一片值得去哪里”；
- Smac 决定“满足车辆约束的全局路线是什么”；
- MPPI 决定“此刻发什么速度才能沿路线走且避障”；
- 底盘驱动只是传输控制命令，不负责 frontier 或全局路径规划。

### 4.4 地图、全局代价地图和局部代价地图不是同一个东西

| 数据 | 坐标系 | 范围 | 内容 | 用途 |
| --- | --- | --- | --- | --- |
| `/map` | `map` | 已建区域 | slam_toolbox 输出的占据栅格 | 保存地图、frontier 检测、全局静态基础 |
| global costmap | `map` | 全局 | `/map` 静态层 + `/scan` 障碍层 + 膨胀层 | 全局规划、探索目标实时安全复核 |
| local costmap | `camera_init` | 机器人周围 `4 m × 4 m` 滚动窗口 | `/scan` 障碍层 + 膨胀层 | MPPI 局部避障、探索器当前位置安全检查 |

global costmap 设置 `track_unknown_space=true`，因为自主探索必须区分未知空间和已知空间。Planner 设置 `allow_unknown=true`，但探索器生成的最终观察位本身必须位于已知自由区。

## 5. 坐标系、里程计和时间关系

### 5.1 主 TF 链

```text
map
└── camera_init
    └── body
        └── fastlio_base_footprint
```

| 坐标系 | 由谁维护 | 含义 |
| --- | --- | --- |
| `map` | slam_toolbox | 二维地图全局坐标系 |
| `camera_init` | FAST-LIO 初始化并连续维护 | FAST-LIO 局部连续里程计坐标系 |
| `body` | FAST-LIO | IMU/雷达机体参考系 |
| `fastlio_base_footprint` | 静态 TF | 建图和导航使用的底盘地面参考点 |

当前静态变换：

```text
body -> fastlio_base_footprint
x = -0.188 m
y = 0.0 m
z = -0.25 m
roll = pitch = yaw = 0
```

项目记录假设 MID360 body 原点位于底盘参考点前方约 `0.188 m`、上方约 `0.25 m`，所以发布逆变换。

### 5.2 为什么不用共享的 `base_footprint`

其他系统可能已经维护：

```text
odom_combined -> base_footprint
```

本建图链使用独立的 `fastlio_base_footprint`，避免同一个 child frame 同时被两条 TF 链控制而形成多父节点或竞争发布。

### 5.3 `/Odometry`、`/odom` 和 TF 的区别

- FAST-LIO 的位姿和 TF 是当前地图栅格化与 Nav2 全局位姿的主要依据；
- WHEELTEC 驱动发布 `/odom`，Nav2 controller/BT 配置使用它获得底盘速度反馈接口；
- `velocity_smoother` 当前使用 `OPEN_LOOP`，即平滑器不依赖闭环里程计修正；
- Topic 中有里程计消息不代表 TF 一定完整，TF 正常也不代表底盘 `/odom` 反馈频率正确，两者要分别检查。

### 5.4 时间和队列为何重要

点云、Scan、TF 和 costmap 都带时间戳。若 CPU 负载导致旧点云排队：

```text
旧点云晚到
  ↓
生成时间戳落后的 /scan
  ↓
TF 缓存已无法提供对应时刻的变换
  ↓
slam_toolbox 或 costmap 丢弃观测
  ↓
地图停止更新、障碍陈旧、规划/控制异常
```

因此自主模式把点云转 Scan 队列和 QoS relay 队列都设置为 1，设计原则是“实时避障宁可丢旧帧，不传播历史帧”。

当前多处 TF tolerance 设为约 `2 s`，用于吸收 FAST-LIO、slam_toolbox 和 Nav2 处理延迟；它不能修复持续积压或错误时间基准。

## 6. 共同建图链逐层原理

### 6.1 Livox 驱动层

启动文件：

```text
src/my_robot_bringup_fastlio/launch/fastlio_mid360.launch.py
```

它首先启动 `livox_ros_driver2` 的 MID360 ROS 2 launch，发布：

- `/livox/lidar`：Livox `CustomMsg` 点云；
- `/livox/imu`：`sensor_msgs/Imu`。

FAST-LIO 配置中 `lidar_type=1`，必须与 CustomMsg 模式一致。若驱动改成普通 PointCloud2，而配置未同步修改，FAST-LIO 预处理会不匹配。

### 6.2 FAST-LIO2 层

FAST-LIO2 的核心思想：

1. 用 IMU 对状态进行高频传播，估计姿态、速度、位置和零偏；
2. 按逐点时间对一帧激光点云去运动畸变；
3. 在当前位姿预测下，把点云与局部增量地图做点到平面匹配；
4. 使用迭代误差状态卡尔曼滤波更新位姿；
5. 把新点插入 ikd-Tree 局部地图并维护滑动区域；
6. 发布连续里程计、TF、路径和配准点云。

当前共同关键参数：

| 参数 | 当前值 | 含义 |
| --- | ---: | --- |
| `point_filter_num` | `3` | 点云预处理约每 3 个有效点取 1 个 |
| `max_iteration` | `3` | 每帧滤波最大迭代次数 |
| `filter_size_surf` | `0.5 m` | 当前帧体素滤波尺寸 |
| `filter_size_map` | `0.5 m` | 地图插入体素尺寸 |
| `scan_rate` | `10 Hz` | MID360 扫描频率配置 |
| `fov_degree` | `360°` | 水平完整视场 |
| `det_range` | `100 m` | FAST-LIO 局部匹配探测范围参数 |
| `extrinsic_est_en` | `true` | 以配置外参为初值在线估计雷达—IMU 外参 |
| `dense_publish_en` | `false` | 发布降采样点云，降低负载 |
| `scan_bodyframe_pub_en` | `true` | 发布二维投影需要的 body 点云 |

手动与自主配置差异：

| 项目 | 手动 | 自主 | 设计原因 |
| --- | ---: | ---: | --- |
| 雷达盲区 `blind` | `0.50 m` | `0.20 m` | 自主避障保留更近障碍 |
| `/Laser_map` 累计三维图 | 开 | 关 | 自主长时间运行避免持续累计和序列化负载 |
| FAST-LIO PCD 保存 | 开 | 关 | 自主交付物以二维图为主 |

FAST-LIO 失败的典型表现：

- `camera_init -> body` TF 不连续；
- `/cloud_registered_body` 不发布；
- 三维点云墙面重影或尺度错误；
- 静止时轨迹明显漂移；
- IMU 初始化或点云预处理持续报错。

### 6.3 三维点云投影二维 Scan

节点订阅：

```text
/cloud_registered_body
```

节点输出：

```text
/scan_raw
```

处理过程：

1. 把点云变换到 `fastlio_base_footprint`；
2. 只保留高度 `[-0.5, 0.8] m` 的点；
3. 把水平方向分成角度桶，当前约 `0.0087 rad` 一个桶；
4. 每个角度保留合适的最近距离；
5. 输出 360° LaserScan，最大距离 `20 m`。

手动模式 `range_min=0.50 m`、队列 10；自主模式 `range_min=0.20 m`、队列 1。

需要特别理解高度裁剪：三维点云里存在地面、天花板、桌面和高处结构，但二维导航只需要特定高度范围内能代表车辆碰撞风险的截面。裁剪过窄会漏障碍，过宽可能把地面、顶部或无关结构投进二维图。

### 6.4 Scan QoS relay

`pointcloud_to_laserscan` 输出 `/scan_raw` 后，自定义 `scan_qos_relay`：

- 用 SensorDataQoS/Best Effort 订阅；
- 用 Reliable + Volatile 发布 `/scan`；
- 不修改原始时间戳；
- 当前输入和输出队列深度均为 1。

它解决的是 DDS QoS 兼容和实时队列问题，不负责滤波、坐标变换或障碍判断。

正常系统要求：

```text
/scan Publisher count = 1
```

多个 `/scan` 发布者会让 slam_toolbox 和 costmap 同时接收不同来源或不同时间基准的数据。

### 6.5 slam_toolbox 二维栅格化

当前配置：

```yaml
map_frame: map
odom_frame: camera_init
base_frame: fastlio_base_footprint
scan_topic: /scan
mode: mapping
resolution: 0.05
scan_queue_size: 5
use_scan_matching: false
do_loop_closing: false
```

`scan_queue_size: 5` 是针对实测中扫描等待 TF 时 "queue is full" 丢帧行为
所做的项目本地调优；上游对 async 模式的指导是 `1`，本值为已知偏离，不是
通用推荐。

当前架构中，slam_toolbox 的主要职责不是重新估计轨迹，而是：

1. 从 TF 获取 Scan 采集时机器人在 `camera_init` 中的位姿；
2. 按该位姿把激光束投进二维栅格；
3. 更新自由、占用和未知单元；
4. 发布 `/map` 及 `map -> camera_init`。

为什么关闭二维 scan matching：项目曾观察到长直走廊的二维扫描高度重复，二维匹配会低估前进位移，使二维地图长度明显小于 FAST-LIO 三维基准。

为什么关闭二维回环：相似房间和相似走廊曾出现错误关联，导致地图折叠或重影。

这两个开关带来的限制是：系统不利用二维 SLAM 修正 FAST-LIO 的长期漂移。若未来要重新开启，必须基于同一 rosbag 做单变量对照，不能同时修改多个匹配和回环参数。

### 6.6 地图自动保存

`map_autosaver` 订阅最新 `/map`，提供：

- 每 60 秒周期备份；
- `/map_autosaver/save_now` 手动/程序触发保存；
- 正常 ROS 退出时保存；
- 自主探索完成时由探索器调用保存服务。

PGM 编码规则：

- 占用概率 `>= 0.65`：黑色；
- 自由概率 `<= 0.25`：白色；
- 中间值和未知：灰色。

保存过程先写 `.tmp` 再 rename，避免正式文件只写到一半。周期保存更新的是本次任务启动时确定的同一文件名，不会每分钟生成一套新文件。文件写入是同步 I/O，当前没有显式的文件 I/O 超时。

## 7. 手动建图操作手册

### 7.1 使用场景

优先使用手动建图的情况：

- 首次验证雷达、FAST-LIO、TF、Scan 和 `/map`；
- 环境狭窄或人员密集，不适合自主测试；
- 需要人工决定覆盖路线；
- 自主模式异常，需要验证共同建图链是否仍稳定；
- 需要查看 `/Laser_map` 三维累计点云或保存 PCD。

### 7.2 启动前检查

在机器人上检查串口和底盘服务：

```bash
ls -l /dev/wheeltec_controller
systemctl is-active robot-base.service
systemctl --no-pager --full status robot-base.service
```

进入隔离环境：

```bash
cd ~/zzj_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
```

检查是否已有重复建图节点：

```bash
ros2 node list
ros2 topic info /scan
ros2 topic info /map
```

若另一个建图 launch 正在运行，先在其原终端 Ctrl-C 正常结束并确认地图保存，不要叠加启动。

### 7.3 启动手动建图

机器人本地图形桌面：

```bash
ros2 launch my_robot_bringup_fastlio manual_mapping.launch.py
```

普通 SSH 没有图形环境时：

```bash
ros2 launch my_robot_bringup_fastlio manual_mapping.launch.py start_rviz:=false
```

默认复用 `robot-base.service`。只有底盘服务已明确停止时才允许：

```bash
ros2 launch my_robot_bringup_fastlio manual_mapping.launch.py start_base:=true
```

### 7.4 启动键盘遥控

另开一个已加载同样 ROS 环境的终端：

```bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard
```

操作建议：

- 先静止数秒，等待 FAST-LIO 初始化和 `/map` 出现；
- 低速起步，先在开阔区验证前进、倒车和转向方向；
- 避免突然大加速、大角速度和剧烈碰撞；
- 观察三维墙面是否稳定，再判断二维地图；
- 分区覆盖，避免无目的长距离往返；
- 当前没有回环修正，走回起点不会自动消除累计漂移。

### 7.5 RViz 应观察什么

| 显示项 | Topic/数据 | 用途 |
| --- | --- | --- |
| FAST-LIO 3D Map | `/Laser_map` | 判断三维地图是否先漂移、重影 |
| Current Scan | `/cloud_registered` | 查看当前配准帧 |
| Path/Odometry | FAST-LIO 路径与里程计 | 查看轨迹连续性 |
| 2D Map | `/map` | 查看最终二维占据栅格 |
| Projected Scan | `/scan` | 检查障碍投影和车体附近盲区 |
| TF | TF display | 检查坐标链是否完整 |

判断顺序必须是：

```text
先看 FAST-LIO 三维是否正确
  ↓
再看 /scan 是否和真实障碍一致
  ↓
最后判断二维 /map
```

如果三维本身已经漂移，调整 slam_toolbox 不能解决上游问题。

### 7.6 手动保存与指定名称

立即保存：

```bash
ros2 service call /map_autosaver/save_now std_srvs/srv/Trigger '{}'
```

使用固定名称和目录：

```bash
ros2 launch my_robot_bringup_fastlio manual_mapping.launch.py \
  map_name:=floor1 \
  map_output_dir:=$HOME/maps/nav2
```

关闭周期备份但保留退出保存：

```bash
ros2 launch my_robot_bringup_fastlio manual_mapping.launch.py \
  map_autosave_interval:=0
```

完全关闭自动保存：

```bash
ros2 launch my_robot_bringup_fastlio manual_mapping.launch.py \
  enable_map_autosave:=false
```

### 7.7 正常停止

1. 先停止遥控输入并确认车辆静止；
2. 在建图 launch 终端按一次 Ctrl-C；
3. 等待终端出现 `Saved ... (shutdown)`；
4. 检查 PGM 和 YAML 都存在；
5. 再关闭终端或 SSH。

检查文件：

```bash
ls -lh ~/maps/manual_mapping/
```

### 7.8 手动建图完成检查

```bash
ros2 topic info /scan
ros2 topic info /map
ros2 run tf2_ros tf2_echo camera_init fastlio_base_footprint
```

期望：

- `/scan` 和 `/map` 各只有一个发布者；
- TF 连续输出，无持续中断；
- 三维墙面和二维墙面尺度大致一致；
- PGM/YAML 同名且 YAML 指向正确的 PGM 文件；
- 地图原点、分辨率和环境方向符合预期。

## 8. 自主建图完整技术逻辑

### 8.1 启动编排与预期时序

正式入口：

```text
autonomous_exploration.launch.py
├── autonomous_mapping.launch.py
│   ├── 可选 base_serial.launch.py
│   ├── cmd_vel_shutdown_guard
│   ├── map_autosaver
│   ├── fastlio_2d_slam.launch.py
│   │   ├── Livox 驱动：立即启动
│   │   ├── FAST-LIO：约 2 s 后启动
│   │   ├── Scan converter/relay：约 5 s 后启动
│   │   └── slam_toolbox/RViz：约 8 s 后启动
│   └── Nav2：默认约 10 s 后启动
└── ackermann_explore：默认约 30 s 后启动
```

Timer 只是减小启动竞态，不代表机器性能异常时一定已准备好。因此探索器还会主动等待 Nav2 lifecycle active、地图/TF/代价地图新鲜。

### 8.2 Nav2 各节点职责

| 节点/模块 | 职责 |
| --- | --- |
| `planner_server` | 接收目标，用 Smac Hybrid-A* 计算全局路径 |
| `controller_server` | 用 MPPI Ackermann 跟踪路径并输出速度 |
| `bt_navigator` | 执行 NavigateToPose 行为树、重规划和恢复 |
| global costmap | 全局静态地图、实时障碍和膨胀代价 |
| local costmap | 机器人附近滚动障碍和膨胀代价 |
| `velocity_smoother` | 限制速度与加速度变化，当前为 OPEN_LOOP |
| lifecycle manager | 按顺序 configure/activate Nav2 节点 |

当前核心参数：

| 类别 | 当前值 |
| --- | --- |
| Planner | `nav2_smac_planner/SmacPlannerHybrid` |
| 搜索模型 | `REEDS_SHEPP`，允许前进和倒车 |
| 最小转弯半径 | Planner 与 MPPI 都为 `0.80 m`（工程假设，仓库内无实测标定依据） |
| Controller | `nav2_mppi_controller::MPPIController` |
| MPPI 模型 | `Ackermann` |
| 控制频率 | `15 Hz`（`model_dt 0.07`，见下方时序 caveat） |
| 速度范围 | 前进 `0.22 m/s`，倒车 `-0.12 m/s`，角速度绝对值 `0.30 rad/s` |
| footprint | `0.44 m × 0.35 m` 矩形配置 |
| 膨胀半径 | local/global 均为 `0.50 m` |
| global costmap | static + obstacle + inflation |
| local costmap | obstacle + inflation，`4 m × 4 m` 滚动窗口 |

各参数的完整语义与逐项解释以《[手动建图与自主建图技术栈及实现原理](手动建图与自主建图技术栈及实现原理.md)》为单一技术事实源；本表仅作速查。

MPPI 时序 caveat：`controller_frequency=15 Hz`（周期约 `0.0667 s`）与
`model_dt=0.07` **不相等**——按 Humble MPPI 行为会触发上游警告且
control-sequence shifting 关闭（历史 20 Hz / 0.05 配置为相等分支、shifting
ON，见 2026-07-26 实机日志）。该组合没有已恢复的运行日志证据，属已知上游
警告 / 恢复期 field tuning，不是最优或已验证配置。

### 8.3 为什么是 Smac Hybrid-A* + MPPI Ackermann

阿克曼底盘不能像差速或麦轮底盘一样原地改变朝向。

Smac Hybrid-A* 在 `(x, y, yaw)` 状态空间搜索，而不是只在二维位置格子中搜索；Reeds-Shepp 模型允许有限倒车，并考虑最小转弯半径。

MPPI 在短时域中采样大量候选控制序列，综合：

- 运动学约束；
- footprint 碰撞；
- 障碍排斥；
- 路径对齐和跟随；
- 目标位置和朝向；
- 前进偏好；
- 控制平滑性。

它选择代价较低的控制序列并输出 `/cmd_vel`。Planner 决定全局几何可达性，Controller 负责局部动态执行，两者的最小转弯半径必须语义一致。

### 8.4 为什么行为树删除 Spin

默认 Nav2 恢复常包含原地旋转。阿克曼车无法原地旋转，强行执行会导致：

- 路径/控制意图与真实车辆不一致；
- 靠墙时产生危险转向；
- 恢复行为长时间失败。

当前自定义行为树：

- 每约 1 秒重新规划 NavigateToPose 路径；
- 规划或跟踪失败时可清理相应代价地图；
- 恢复阶段允许等待；
- 不执行 Spin；
- behavior server 也只启用 Wait。

日志中的 `Passing new path to controller` 常表示同一个 NavigateToPose 目标被行为树重新规划，不等于探索器换了新目标。

### 8.5 Frontier 探索基本概念

二维地图栅格分三类：

- 自由：已观测且可通行；
- 占用：已观测障碍；
- 未知：尚未观测。

frontier 是“已知自由区与未知区的边界”。机器人到 frontier 附近的已知自由观察位后，MID360 会看到新区域，地图扩大，然后探索器寻找下一组 frontier。

旧的通用 `explore` 倾向按欧氏距离选择 frontier 质心，不能充分表达阿克曼可达性。当前 `ackermann_explore` 不把未知区质心直接交给 Nav2。

### 8.6 `ackermann_explore` 一轮决策

```text
1. 等待 planner/controller/bt_navigator 都 active
2. 检查 /map、TF、global/local costmap 是否新鲜
3. 记录本次任务首次有效机器人位姿，作为返航起点
4. 从 /map 提取 frontier cluster
5. 按未知面积、frontier 长度、距离和车头方向预排序
6. 在真实 frontier 边界上抽样锚点
7. 朝已知自由区生成面向未知区的观察位姿
8. 检查目标必须在已知自由区
9. 检查 footprint 圆形包络净空、目标后方净空和最小行程
10. 用实时 global costmap 再次检查候选安全性
11. 逐个调用 ComputePathToPose，让 Smac 验证真实阿克曼路径
12. 分析路径长度、倒车、换挡、转向变化、净空和信息增益
13. 过滤违反倒车/换挡限制的路径
14. 选综合得分最低的观察位
15. 最后再做一次 live costmap 安全检查
16. 发送一个 NavigateToPose
17. 保持当前目标，直到成功、失败、取消或超时
18. 地图更新后进入下一轮
```

当前候选关键限制：

| 参数 | 当前值 | 作用 |
| --- | ---: | --- |
| `candidate_standoff` | `0.80 m` | 观察位与 frontier 的基本距离 |
| `candidate_standoff_max` | `1.20 m` | 最大后退观察距离 |
| `footprint_clearance` | `0.50 m` | 候选周围所需净空包络 |
| `candidate_back_clearance_distance` | `0.40 m` | 目标后方调整空间 |
| `minimum_candidate_travel_distance` | `0.50 m` | 避免反复发送到达容差内的近目标 |
| `max_frontiers_to_evaluate` | `6` | 控制昂贵 Hybrid-A* 评估数量 |
| `max_reverse_fraction` | `0.55` | 限制主要靠倒车探索 |
| `max_reverse_length` | `0.80 m` | 限制累计倒车距离 |
| `max_gear_switches` | `2` | 限制频繁前后切换 |

### 8.7 候选评分的含义

探索器倾向选择：

- 全局路径短；
- 倒车距离少；
- 前进/倒车切换少；
- 初始转向小；
- 全程转向变化小；
- 障碍净空大；
- 能看到更多未知面积。

这不是“离机器人最近的 frontier 就最好”，而是“对当前阿克曼车辆安全、可达且信息收益较高的观察位更好”。

### 8.8 导航期间的监控和取消

探索器并行检查：

- 目标在 global costmap 中是否仍有足够净空；
- 当前机器人在 local costmap 中是否接近致命障碍；
- global/local costmap 是否过期；
- action feedback 的剩余距离是否改善；
- 实际位置或朝向是否变化；
- `35 s` 内是否存在导航进展；
- 候选路径评估是否超过 `40 s`。

致命障碍可立即取消当前 frontier 导航。TF、未知区或 costmap 暂时陈旧等瞬态条件需要连续达到配置次数才取消，减少一次调度抖动造成误判。

导航失败的 frontier 会进入临时抑制记录：默认 `90 s` 后过期，或地图 revision 变化达到阈值后提前重新开放。它不是永久黑名单。

### 8.9 受阻与完成的严格区别

只有下面条件同时成立，探索器才累计完成证据：

1. `/map` 新鲜；
2. 地图至少 `10 s` 没有变化；
3. 起点记录后已超过 `60 s` 启动保护期；
4. 确实检测不到任何 frontier；
5. 上述“无 frontier”在同一稳定地图 revision 上连续出现 3 个周期。

下列情况一律属于“暂时受阻”，不是完成：

- frontier 存在，但没有满足净空的观察位；
- frontier 存在，但 Smac 找不到路径；
- 所有 frontier 暂时在失败抑制记录中；
- map、costmap 或 TF 陈旧；
- Nav2 lifecycle 未 active；
- action server 不可用或路径评估超时。

如果机器人长期原地等待，要从日志判断它在哪个受阻条件，不要通过简单减少完成阈值让系统“假完成”。

### 8.10 完成、返航、保存和退出

```text
确认探索完成
  ↓
发布 EXPLORATION_COMPLETE
  ↓
return_to_start=true ?
  ├── 是：NavigateToPose 返回首次记录位姿，最长等待 120 s
  └── 否：直接收尾
  ↓
无论返航成功、失败、拒绝还是超时
  ↓
取消剩余 action，重复发布零速度
  ↓
调用 /map_autosaver/save_now
  ↓
保存成功或明确超时
  ↓
探索器退出
  ↓
OnProcessExit 关闭整组 autonomous launch
```

返航失败不会阻止最终保存。保存失败也会在明确超时后结束收尾，避免系统无限卡在 finalization。

## 9. 自主建图操作手册

### 9.1 启动前物理检查

- 场地内人员知晓车辆将自主移动；
- 硬件急停可用且现场人员能立即触达；
- 地面无明显台阶、悬崖或 MID360 难以感知的危险；
- 车体、雷达、线缆、轮胎和转向机构无松动；
- 初始位置有足够前后左右空间，避免初始地图太小；
- 确认本次测试是否允许倒车和返航。

### 9.2 软件预检

```bash
ls -l /dev/wheeltec_controller
systemctl is-active robot-base.service
ros2 pkg prefix nav2_bringup
ros2 pkg prefix nav2_mppi_controller
```

进入隔离环境后检查共同话题：

```bash
ros2 topic list
ros2 node list
```

若底盘服务显示 active 但没有实际驱动节点，可从 Mac 执行：

```bash
./scripts/robot.sh restart-base
```

它通过 systemd 重启完整服务组并验证 `wheeltec_robot_node`，不要用模糊 `pkill` 替代。

### 9.3 第一步：自主选择 dry run

```bash
ros2 launch my_robot_bringup_fastlio autonomous_exploration.launch.py \
  explorer_dry_run:=true
```

该模式会：

- 启动共同建图链和 Nav2；
- 检测 frontier；
- 生成候选观察位；
- 调用 Smac Hybrid-A*；
- 在 RViz 显示候选与选择结果；
- 不发送 NavigateToPose，因此不会由探索器驱动车辆。

注意：其他 `/cmd_vel` 发布者仍可能让车辆移动。dry run 只保证探索器不发导航目标，不等于系统层面的硬件禁动。

### 9.4 第二步：单目标 Nav2 测试

启动共同建图链和 Nav2，但不启动探索器：

```bash
ros2 launch my_robot_bringup_fastlio autonomous_mapping.launch.py
```

等待 Nav2 active 后，在 RViz 中给一个开阔、短距离、满足阿克曼转弯空间的单目标。

该实验验证：

```text
/map + TF + costmap
  ↓
Smac Hybrid-A* 路径
  ↓
MPPI Ackermann /cmd_vel
  ↓
WHEELTEC 底盘真实运动
```

若单目标导航不稳定，不应继续调探索器，因为探索器只是在重复调用同一套 Nav2 能力。

### 9.5 第三步：完整自主探索

机器人本地图形桌面：

```bash
ros2 launch my_robot_bringup_fastlio autonomous_exploration.launch.py
```

SSH/headless：

```bash
ros2 launch my_robot_bringup_fastlio autonomous_exploration.launch.py \
  start_rviz:=false
```

常用覆盖项：

```bash
# 禁止完成后返航
return_to_start:=false

# 只保留完成/退出保存，关闭周期保存
map_autosave_interval:=0

# 完全关闭地图自动保存
enable_map_autosave:=false

# 不启动探索器，只验证自主底座时应直接使用 autonomous_mapping.launch.py
```

### 9.6 运行中如何判断系统状态

| 观察 | 正常含义 | 异常含义 |
| --- | --- | --- |
| 地图持续扩张 | 新区域正在被观测 | 地图不动可能是机器人未动、Scan/TF 中断或到达已知区域 |
| global path 周期更新 | 同一目标在重规划 | 需结合 action UUID 判断是否真的换目标 |
| 机器人短暂停等 | Nav2 规划、恢复或探索重新评估 | 长时间等待需看受阻日志 |
| frontier 标记变化 | 地图更新导致边界变化 | 标记完全不出现需检查 `/map` 与探索器 |
| local costmap 障碍随环境变化 | `/scan` 实时更新 | 障碍冻结可能是 Scan/TF/队列问题 |
| 周期出现 Saved 日志 | 地图备份正常 | 无保存日志需检查 `/map`、目录和 autosaver |

### 9.7 正常停止自主建图

1. 现场人员准备接管；
2. 在 launch 终端按一次 Ctrl-C；
3. 确认车辆立即停止；
4. 等待 `cmd_vel_shutdown_guard` 零速日志；
5. 等待 `map_autosaver` 的 shutdown 保存结果；
6. 检查 PGM/YAML；
7. 确认公共 `robot-base.service` 仍按部署设计运行。

紧急情况下优先硬件急停，不要为了等待保存日志延误停车。

## 10. 底盘控制与安全链

### 10.1 `/cmd_vel` 到 STM32

```text
Nav2 velocity_smoother 或人工 teleop
        ↓ /cmd_vel (geometry_msgs/Twist)
turn_on_wheeltec_robot
        ↓ avoid_obstacle（当前配置关闭时应基本透传）
linear.x × 1000
linear.y × 1000
angular.z × 1000
        ↓ 11 字节控制包
/dev/wheeltec_controller @ 115200
        ↓
STM32 下位机
        ↓
驱动电机和转向机构
```

ROS 驱动没有根据轴距把 `angular.z` 显式换算为舵角或曲率。因此必须保留一个关键未知项：STM32 在 `senior_akm` 模式下如何解释 `angular.z`。

在固件/协议未确认前，不要把 Nav2 参数中的角速度、最小转弯半径和实车舵角关系当成已经闭环标定。

### 10.2 `/odom` 反馈

WHEELTEC 驱动读取串口反馈后发布 `/odom`。项目曾把串口读取超时从 2000 ms 缩短到 20 ms，避免串口无数据时 ROS callback 长时间饥饿。

检查：

```bash
ros2 topic hz /odom
ros2 topic echo /odom --once
```

历史记录曾达到约 20 Hz，但接手时应以当前实测为准。

### 10.3 三层软件停车保护

| 保护层 | 触发条件 | 行为 |
| --- | --- | --- |
| 底盘驱动 watchdog | 收到过指令后 `0.5 s` 没有新 `/cmd_vel` | 直接向 STM32 发送零速 |
| `cmd_vel_shutdown_guard` | autonomous launch 收到 SIGINT/SIGTERM | 连续发布 10 次零速度 |
| 探索器 final stop burst | 任务完成并进入收尾 | 连续发布零速度后退出 |

这些保护依赖软件、ROS、串口和下位机仍部分可用。它们不能替代硬件急停。

### 10.4 车辆继续移动时的处理优先级

```text
1. 立即硬件急停/切断驱动输出
2. 确保人员远离车辆
3. 再检查 /cmd_vel 发布者和底盘服务
4. 保存日志，不要先改参数
5. 明确是哪一层仍在发非零指令
```

诊断命令：

```bash
ros2 topic info /cmd_vel --verbose
ros2 topic echo /cmd_vel
journalctl -u robot-base.service -n 100 --no-pager
```

## 12. 分层验收流程

执行纪律（吸收自 2026-08-04 诊断记录的分层验证方法）：必须自下而上逐层
进行，**任何一层失败时停止并修复后才进入下一层**；不要跳层测试，也不要在
多层同时存在未解释故障时直接重构整个系统。怀疑探索层问题时，先确认下层
（传感器/TF、底盘几何、单目标 Nav2）已稳定。

### 12.0 底盘几何与曲率预检（进入自主模式前）

来自历史诊断记录的可复用方法：在安全空旷区域，分别以固定的正/负
`angular.z`（配合低速 `linear.x`）驱动底盘，实测转弯半径与方向：

- 验证 `angular.z` 的实际转向方向与符号约定一致；
- 用实测弧线半径对照 Nav2 配置的 `0.80 m` 最小转弯半径（该值当前为工程
  假设，本预检正是把它变成实测依据的第一步）；
- 确认 STM32 对 `angular.z` 字段的语义（放大倍数、是否舵角/曲率）与
  ROS 侧理解一致，双向都要测。
- 预检未通过时，不要进入 E/F 层自主测试。

### 12.1 A 层：构建与安装一致性

通过条件：

- `./scripts/robot.sh build` 全量成功；
- `audit-install` 没有未解释的 `DIFF`、`INSTALL_ONLY` 或 broken link；
- Nav2 包前缀为 `/opt/ros/humble`；
- 当前运行源码、install 和文档日期可追溯。

### 12.2 B 层：静止传感器与 TF

只启动手动建图，不驾驶。

通过条件：

- `/livox/lidar`、`/livox/imu` 连续；
- FAST-LIO 初始化成功；
- `/cloud_registered_body`、`/scan`、`/map` 出现；
- TF 链完整；
- 静止时三维点云没有明显持续漂移。

### 12.3 C 层：手动建图

进行短距离、低速、可重复路线。

通过条件：

- 三维墙面稳定；
- `/scan` 与真实障碍相符；
- 二维地图尺度与三维基准基本一致；
- 保存出的 PGM/YAML 可读取；
- Ctrl-C 后车辆停止且最终保存完成。

### 12.4 D 层：自主 dry run

通过条件：

- Nav2 三个核心 lifecycle 节点 active；
- frontier 能检测；
- 候选位于已知自由区；
- ComputePathToPose 能返回部分可行路径；
- RViz 选点方向和净空肉眼合理；
- 不发送 NavigateToPose。

### 12.5 E 层：单目标 Nav2

不启动探索器，只给一个短距离目标。

通过条件：

- Smac 路径满足阿克曼形态，不要求原地旋转；
- MPPI 输出方向与路径一致；
- 实车转向方向、倒车语义和 `/cmd_vel` 一致；
- local costmap 障碍靠近时能安全减速/停下；
- 目标成功、失败和取消都能正确停车。

### 12.6 F 层：完整自主探索

逐步从单房间、开阔区扩大到走廊和多房间。

通过条件需要项目负责人定义量化阈值，至少记录：

- 地图覆盖率；
- 任务完成率；
- 最小障碍距离；
- 撞击/急停次数；
- 规划失败和控制 abort 次数；
- 长时间受阻次数及原因；
- 返航结果；
- 最终地图保存结果；
- 运行版本、配置哈希和日志路径。

程序启动、某一次测试通过或“地图看起来不错”都不足以代表完整验收。

## 13. 故障定位总方法

### 13.1 永远按数据链从上游到下游查

```text
硬件/网络
  ↓
Livox 点云和 IMU
  ↓
FAST-LIO 位姿、TF、三维点云
  ↓
/scan_raw 和 /scan
  ↓
slam_toolbox /map
  ↓
global/local costmap
  ↓
Smac 路径
  ↓
MPPI /cmd_vel
  ↓
ROS 底盘驱动和串口
  ↓
STM32 和真实车辆运动
```

不要在上游数据已异常时直接调下游权重。

### 13.2 不确定故障的实验规则

每轮只验证一个主要假设：

1. 写清楚可观察现象；
2. 区分事实、证据支持的推断和未验证假设；
3. 选择一个最小实验；
4. 每次只改变一个主要变量；
5. 运行前写出预期结果和什么结果会推翻假设；
6. 保存实际日志、Topic、TF 和地图；
7. 连续两次不支持同一假设时停止堆补丁，回到稳定基线重新分析。

### 13.3 常见现象与第一检查点

| 现象 | 首先检查 | 不应先做什么 |
| --- | --- | --- |
| 完全没有 `/livox/lidar` | MID360 供电、网络、Livox 驱动 | 调 slam_toolbox |
| 有雷达无 FAST-LIO 点云 | `/livox/imu`、消息类型、FAST-LIO 配置与日志 | 调 Nav2 |
| 有三维点云无 `/scan` | body TF、高度裁剪、converter 节点、队列 | 调 frontier |
| 有 `/scan` 无 `/map` | `/scan` 发布者数量、QoS、TF、slam_toolbox 日志 | 调 MPPI |
| 手动地图正常、自主不动 | Nav2 lifecycle、action server、costmap、探索器受阻日志 | 重写 SLAM |
| 有路径但车不动 | `/cmd_vel`、底盘节点、串口、STM32、watchdog | 放宽 frontier |
| 车实际转向与路径相反 | `/cmd_vel angular.z`、车型模式、STM32 语义、机械转向 | 调信息增益权重 |
| 撞墙/贴墙 | 立即急停；再查 Scan 时效、costmap、footprint、TF、底盘执行 | 一次改多个安全参数 |
| 原地等待 | 区分无 frontier、无候选、无路径、costmap 陈旧、Nav2 未 active | 降低完成条件让它退出 |
| 二维图缩短/重影 | 先比较 FAST-LIO 三维与轨迹，再查 Scan/TF/slam_toolbox | 直接开启回环 |
| Ctrl-C 后还移动 | 硬件急停、`/cmd_vel` 发布者、watchdog、guard 日志 | 等地图保存完再处理 |
| 保存失败 | `/map` 是否存在、save service、目录权限、磁盘空间 | 只看 launch 是否还活着 |

## 14. 典型故障排查步骤

### 14.1 `/scan` 或 `/map` 有多个发布者

已确认事实：本系统设计要求各只有一个发布者。

最小检查：

```bash
ros2 topic info /scan --verbose
ros2 topic info /map --verbose
ros2 node list
```

支持“重复节点”假设的结果：看到不同节点同时发布同一 Topic。

会推翻该假设的结果：发布者确实只有一个，此时转查时间戳、TF 和数据内容。

不要用模糊进程名批量杀节点。回到启动它们的终端或对应 systemd 服务，按所属 launch 正常停止。

### 14.2 TF future/past extrapolation 或 queue full

候选假设不超过三个：

1. 旧 Scan 积压，消息时间戳落后；
2. FAST-LIO 或 slam_toolbox 处理负载过高，TF 发布不及时；
3. 系统时钟/传感器时间基准不一致。

最小检查：

```bash
ros2 topic hz /scan
ros2 topic echo /scan --once
ros2 run tf2_ros tf2_echo camera_init fastlio_base_footprint
```

自主模式已经使用队列深度 1。若仍持续积压，不应继续单纯增大 `transform_tolerance`；需要测量消息年龄和处理时延。

### 14.3 手动正常，自主撞墙或路径抖动

已确认事实：两种模式共享主体建图链，自主模式新增 costmap、规划、控制、探索和底盘闭环。

建议实验顺序：

1. 运行 `autonomous_mapping.launch.py`，不启动探索器；
2. 只发一个短距离 Nav2 目标；
3. 记录 global path、local costmap、`/cmd_vel` 和实车动作；
4. 若单目标稳定，再运行 explorer dry run；
5. 最后运行完整探索。

能推翻“探索器是主要原因”的证据：不启动探索器的单目标 Nav2 仍稳定复现同类撞墙或控制异常。

### 14.4 探索器长期发呆

先从日志区分：

- `no frontier cells detected`：可能接近完成，但仍要满足稳定与周期条件；
- `frontier cluster(s) remain`：地图未完成，只是候选/路径受阻；
- global/local costmap stale：数据时效问题；
- waiting for lifecycle/action server：Nav2 尚未准备好；
- all frontiers in blacklist：等待抑制过期或地图更新；
- no feasible path：Smac 或车辆几何约束下暂不可达。

只有第一类在稳定条件满足后能成为完成证据。

### 14.5 `robot-base.service` active 但没有底盘节点

可能是外层 launch 还活着，实际串口驱动子进程已经退出。

检查：

```bash
systemctl --no-pager --full status robot-base.service
ros2 node list
journalctl -u robot-base.service -n 100 --no-pager
```

从 Mac 使用项目脚本恢复：

```bash
./scripts/robot.sh restart-base
```

### 14.6 地图文件不存在或损坏

检查：

```bash
ros2 topic echo /map --once
ros2 service list | grep map_autosaver
df -h
ls -ld ~/maps ~/maps/manual_mapping ~/maps/autonomous_mapping
```

调用一次保存服务并读取返回消息。若 PGM 存在但 YAML 不存在，或反之，保存没有形成完整交付物；不要把单个文件交给下游。

## 16. 当前已确认事实与尚未闭环事项

### 16.1 已确认事实

1. 当前源码使用 ROS 2 Humble 接口。
2. 手动与自主模式共享 MID360、FAST-LIO、点云投影、Scan relay、slam_toolbox 和主要 TF。
3. 二维建图当前关闭 scan matching 和 loop closing。
4. 自主模式使用 Smac Hybrid-A*、Reeds-Shepp 和 MPPI Ackermann。
5. Planner 与 Controller 都配置 `0.80 m` 最小转弯半径。
6. local/global costmap 使用同一套 `0.44 m × 0.35 m` footprint。
7. ROS 底盘驱动直接缩放并透传 `angular.z`，没有在 ROS 侧做轴距—舵角换算。
8. 当前探索器导航期间保持一个目标，不按固定周期主动抢占。
9. 当前探索器仅在稳定、真正无 frontier 时完成；有 frontier 但不可达会等待。
10. 当前源码包含返航、最终保存、零速收尾和退出整组 launch 的完整流程。

### 16.2 有证据支持但仍需实机确认

1. 关闭二维 scan matching/loop closure 应能避免历史上的走廊尺度压缩和相似房间误吸附；不同环境仍需验证。
2. 自主模式近场 `0.20 m` 与最新帧队列应改善避障时效；需实测端到端消息年龄。
3. 三层停车保护应覆盖多数正常退出和指令中断；不能证明全部硬件故障都能停车。

### 16.3 尚未验证的关键假设

1. `fastlio_base_footprint` 是否位于车辆规划/控制应使用的真实参考点。
2. `0.80 m` 是否为当前车辆不同方向和速度下的真实最小转弯半径。
3. 当前 footprint 是否覆盖车体、突出物和合理安全余量。
4. STM32 对 `senior_akm` 模式下 `angular.z` 的真实解释。
5. 当前机器人运行的二进制、源码、参数和本文是否完全同版。

### 16.4 缺少的关键证据

- STM32 固件或正式控制协议；
- 轴距、轮距、前后悬、最大舵角、转弯半径标定；
- 当前正式版本完整 rosbag、ROS 日志和 systemd journal；
- `/scan`、TF、costmap 的端到端延迟；
- 探索状态机和安全取消的自动测试；
- 覆盖率、任务成功率和最小障碍距离等验收统计。

## 22. 最终交接结论

当前系统的核心架构是：

```text
MID360 + FAST-LIO2
负责三维感知、点云配准和连续位姿
        ↓
pointcloud_to_laserscan + scan_qos_relay
负责把三维实时观测变为适合二维导航的最新 LaserScan
        ↓
slam_toolbox
按照 FAST-LIO 位姿生成二维 OccupancyGrid，不重复修改轨迹
        ↓
手动：人工驾驶完成环境覆盖
自主：frontier 观察位 + Smac Hybrid-A* + MPPI Ackermann 完成覆盖
        ↓
map_autosaver + 返航 + 多层零速保护
完成地图和任务收尾
```

接手后的最高优先级不是继续增加算法，而是补齐当前系统的物理事实：车辆参考点、footprint、轴距/舵角/转弯半径和 STM32 控制契约；随后以当前真实运行版本完成分层、可复现、可量化的现场验收。

在这些证据补齐之前，所有自主运行都应保持现场监护，并严格区分“代码已经实现”“离线证据支持”和“实机已经验收”这三种状态。
